- **A task's gate runs the project's pre-gate first, and a red there stops it.** When the plan declares `meta.buildCommands.preGate`, a task's gate run takes that command ahead of its own steps and records it first. If it comes back red, the gate's own steps are not started: each is recorded by name as not run, with the reason, and the run is red on the pre-gate - so a broken change costs one fast check rather than the whole gate. A green pre-gate never stands in for the gate: every declared step still runs and decides the verdict. A `preGate` value that cannot be run is recorded as a step that could not run, so the run never reads green over it. The pre-gate runs once: a new phase's default gate no longer includes the `preGate` key, a gate that already names it runs it in place without a separate stage, and the phase gate and the full gate run only what they declare. A green task run that led with the pre-gate still binds the task's commit, because the leading pre-gate step is not read as an entry of the task's gate.
