- **A task can be held with a reason, and a held task is outside both the ready set and the gate's blocked count.** `/audit:task hold <id> --reason "<why>"` sets the new `held` status and records the reason in `blockedReason`; `/audit:task release <id> --reason "<what changed>"` returns it to `pending` and drops the reason. Each writes a journal row (`task.hold`, `task.release`) carrying the reason. A held task is skipped by the ready set, so `/audit:status` does not list it under READY NOW; `--gate --fail-on blocked-tasks` does not count it, and it is not finished work either, so a task waiting on it keeps waiting and a phase over it cannot sign off. `start` refuses a held task, `--force` included, and says to release it first; `block` and `unblock` refuse one and name `release`. The validator asks a held task for its reason, where a blocked task may still have none. `held` is an additive value of the status enum: a plan that holds nothing validates and behaves as before, and an older plugin refuses a plan carrying the word (`COMPATIBILITY.md` lists it under what is not promised). `/audit:status` prints a held task as `Held` under the marker it gives a word it has no glyph for; this change does not teach the report, the panel or the ADO `stateMap` the word.
