- **A task writes its changelog entry as a fragment of its own, and the release assembles `CHANGELOG.md` from them.** A fragment is `changelog.d/<task-id>.<kind>.md` holding the entry's bullets, `kind` being one of the section words this changelog opens sections with (`breaking`, `added`, `changed`, `deprecated`, `removed`, `fixed`, `security`, `documentation`, `compatibility`), so two tasks no longer share `CHANGELOG.md` and the drive can plan them as one wave. `tools/release.py run` appends the fragments under `## [Unreleased]`'s own text, which it leaves as written, when it renames that heading to the version - each kind under a `### <Kind>` heading, kinds in the order above, task ids in numeric order inside a kind - and the release commit deletes the fragments it assembled. A fragment naming no kind or an unknown one, an empty one, or one writing a heading of its own is refused by `release.py changelog-check`, which `tools/verify.sh --only lint` runs, and so is an assembled section that no longer ends with what the fragments assemble to. `CONTRIBUTING.md`'s release step states the rules.
