Audit Plugin Handbook

The manifest is the plan. Commands move work through it, the board mirrors it, and the panel is the same levers with a mouse.

Written against the plugin, not against one repository: every command, flag and default here is the same wherever it is installed. Where a value is yours to supply it appears as <org>, <project> or <phaseId>.

01

Install & update

Two commands, typed into Claude Code rather than a shell. The first registers the marketplace this plugin ships from; the second installs the plugin out of it.

/plugin marketplace add AleksandarBisevac/claude-plugins
/plugin install audit@quality-gates

Requirements are deliberately thin: Python 3.8 or newer, reachable as python3, python or py. On Windows, run inside Git Bash. There is nothing to pip install — the hooks and scripts are standard library only, on purpose, because a guard that needs a dependency is a guard that is switched off on most machines.

Installing arms hooks everywhere

The guard hooks activate in all your projects, not just the one you installed from. That is by design — but the plan gate enforces only once a manifest exists, and merely observes before that. Installing does not start refusing edits in repositories that never opted in.

Scope decides who else gets it

/plugin install takes a --scope, and the choice is about where the enabling record is written — not about which repositories the plugin can read.

ScopeWritten toWho gets it
user~/.claude/settings.jsonevery repository you open; nothing lands in the repo
projectthe repo’s .claude/settings.jsoncommitted, so teammates are prompted to install it too
local.claude/settings.local.jsononly you; the file is gitignored

Installing enables as a side effect — the separate enable verb exists only to switch a disabled plugin back on.

Updating, and why it is three commands

/plugin marketplace update quality-gates
/plugin install audit@quality-gates
/reload-plugins

Each one undoes a different kind of staleness, which is why dropping one usually leaves you on the old version wondering why a documented flag is rejected:

  • marketplace update re-reads the marketplace, so it learns a release exists.
  • install bumps the cached copy and the install record. These drift apart: a record can pin a version long since superseded while a newer copy sits in the cache.
  • reload-plugins makes the new commands appear in the session you already have open — Claude Code reads the command list once, at startup.
A project-scope install pins a version

Installing at project scope pins that repository to the cached version it installed. It does not follow later releases: a repo set up months ago can still be running the version it was installed with while user scope has moved on. Re-run the install in that repository to bump it.

Checking it actually took

/plugin list      # audit@quality-gates, enabled
/audit:status     # renders the manifest, or points you at /audit:init

If /audit:* comes back not recognized, it is nearly always one of two things: the plugin is installed but not enabled, or it was only ever installed at project scope for some other repository. The three update commands above resolve both, and /audit:doctor reports what the hooks will actually use once they do.

02

The model in one minute

Everything hangs off one file — the manifest. It holds phases, each holding tasks, plus bugs and parked proposals. Commands read and write that file; nothing else is the source of truth.

Read the badges

Every command below carries what it touches: read-only writes manifest writes ADO takes lock

One direction at a time

Sync is never bidirectional in a single call. You push, or you pull. That is deliberate — it is what makes a surprise on the board traceable to one invocation.

03

Setup, in brief

The manifest is generated once, before the pull request, so most of you will never run this. It is here so the output makes sense when you see it.

/audit:init writes manifest

Interviews for scope, fans out read-only explorers across the codebase, synthesizes a plan, and shows it for approval before writing anything. What you approve becomes live phases; what you decline is parked as proposals rather than thrown away.

It also asks how to store the manifest: one file, or one file per phase (sharded) for parallel worktrees.

/audit:doctor [--deep] read-only

The first thing to run when something behaves oddly. Reports the interpreter the hooks use, git root, config, manifest and shard integrity, which plan-gate tier is active, build runners, whether hooks have ever fired, and whether the capability policy is inert or never enforced.

A gate that cannot run is not a gate that passed

meta.buildCommands names the commands a phase's sign-off runs, and /audit:doctor checks each one's runner against this machine's PATH. It warns per runner, because a missing one is reported as infrastructure failure, not a red test — and that distinction is the whole value of the check, since one verdict says “your change is wrong” and the other says “nothing was measured”.

The gate is chosen per phase, not per manifest. Each phase's testGate lists which buildCommands keys must pass, so one warning does not disable every phase: where a repo's Python runner is absent, a phase whose gate names only the JS keys still runs a gate that grades. Read the warning against the phase you are about to start, not against the plan as a whole.

Do not answer a missing runner with a new path

Measured on a conda project: buildCommands.pytest read .venv/bin/python, no .venv existed anywhere, and the repair was not a different command. The environment the project already declares in environment.yml — carrying both missing runners — had simply never been created on that machine. Repointing the key would have hidden that.

04

Running phases

A phase is the unit of work and the unit of review. You can run a whole phase, one task, or simply “whatever is next” — and every one of them previews first.

/audit:phase <phaseId> [--dry-run] writes manifest

Runs every ready task in the phase — in parallel where that is safe — until none remain, then runs Phase sign-off: review, the test gate, an invariant check, an optional runtime boot, and the merge.

  • A phase already done is refused; it points you at /audit:review instead of silently re-running.
  • --dry-run prints the plan and mutates nothing.
/audit:phase P0 --dry-run   # see the plan
/audit:phase P0             # then run it
/audit:next [--dry-run] writes manifest

Executes the next ready task — phase order first, then task-id order — and then tells you what became ready.

/audit:run <taskId> [--dry-run] writes manifest

One task by id, with guards on done, blocked and in_progress, plus blocker checks.

/audit:resume writes manifest

Finds the in-progress phase and continues from the first uncommitted task. This is the answer to “my session died mid-phase”.

/audit:review <phaseId> writes manifest

Re-runs sign-off on demand, after fixes — the same review, test gate, invariant check and merge, without re-running the tasks.

/audit:worktree <phaseId> [--remove] writes manifest

Creates a git worktree for a phase and derives its branch, so two people can run two phases at once. Open a Claude session in the printed path and run /audit:phase there.

Sharded manifests merge back conflict-free — that is the reason the layout exists.

/audit:status [--gate] [--fail-on <c1,c2>] [--json] read-only

Phases, tasks, bugs, the ready-now list, and what each pending task is waiting on. No locks, no mutations — safe to run at any time, including mid-phase.

With --gate the same state becomes a CI pass/fail verdict over conditions you choose with --fail-on.

05

Shaping phases & tasks

The plan is not frozen. Four verbs change it, and each one records what it did — these are journalled operations, not edits.

/audit:task add "<title>" [--phase <id>] writes manifest takes lock

Interactive. Allocates the id, initializes every orchestrator field, updates the fileIndex, and revalidates the manifest before it returns.

/audit:task add "Extract the KPI query into a service" --phase P2
/audit:task move <taskId> --to <phaseId> writes manifest takes lock

Renumbers the task into the target phase, rewrites every reference to it, and records a chained task.move journal row. You do not chase the id by hand.

/audit:task cancel <id> --reason "<why>" writes manifest takes lock

Closes a task — or a whole phase — as terminal but not done, recording the reason, the moment and a journal row. Use it instead of deleting: “we decided not to” is information, and a deleted task cannot say it.

/audit:phase priority <phaseId> <tier|--clear> writes manifest

Pins a phase ahead of the others among work that is already ready. It never runs something ahead of its dependency — priority reorders the ready set, it does not override the graph.

Priority is a phase lever, not a task one. Tasks have no priority at all; their order inside a phase comes from the dependency graph and their ids. This reads as /audit:phase because that is what it acts on — /audit:task priority is the legacy spelling and still works.

/audit:bug add "<title>" · list · fix <bugId> · close <bugId> [wontfix] writes manifest

Bugs live in the manifest beside the plan. fix materializes a TDD fix task; the repro test must fail red-first, which is what proves the bug is the bug. Execution itself stays in the normal run commands.

/audit:bug add "Sparkline drops the last day on month boundaries"
/audit:bug fix BUG-3 --phase P1
/audit:run T14

Areas — one repo, two stacks

A phase can carry area: one tag ("backend") or a list for cross-cutting work (["backend","frontend"], grouped under each). meta.areas is the registry that gives a tag properties — a root directory, a description, a default reviewSkill, default executor skills and an advisory owner. Reviewer resolution is phase.reviewSkill → areas[tag].reviewSkill → meta.reviewSkill; executor skills are the area's plus the task's own, deduped, area first. Where a phase carries several tags, written order decides: the first tag whose area declares the field answers.

This is a manifest label and it reaches no board. It groups and filters in status, the report and the panel, and it selects reviewers and skills. It is not System.AreaPath and not a work-item tag — a backend card and a frontend card leave for ADO carrying the same tag set. Where the board has to tell them apart, that is meta.ado.areaPath, or a tag added on the item itself, which a push preserves.

Two asymmetries are worth knowing before registering anything:

  • An absent tag is not a tag. A phase with no area raises nothing at all. The validator warns about an unregistered tag, and only once the manifest registers areas — where it is usually a typo. So leaving a phase untagged stays a legitimate answer when no tag would be true of it, and beats inventing one to fill the field.
  • Registering an area makes its silence visible. An area declaring no skills resolves none, so a task with none of its own warns no skills resolve. The ways out are the task's own skills, defaults on the area, or "skills": null to state that none applies — and that last one is the point: it records the intention, where leaving the warning standing records nothing.
06

Parked proposals

Work that /audit:init proposed and nobody accepted yet lives in proposals[], outside the phases. It is a queue, not a plan — an empty live plan with parked proposals means nothing is scheduled, not that something was lost.

/audit:propose list [all] read-only

Prints id | status | reserved phase (task count) | name | openQuestions. Default shows proposed only; list all adds materialized and dropped history.

/audit:propose materialize <PROP-id> | --all writes manifest takes lock

Materialization is a move, not a re-synthesis. The proposal enters the plan as it was parked. That has a practical consequence worth planning around: if an open question would change what the phase contains, settle it first — otherwise you materialize a phase built on a guess and edit it afterwards.

Phase ids are allocated at materialization, with a collision guard that reports [renamed from …] when it has to pick a new one. So a blockedBy P0 on a parked proposal points at something that does not exist yet — that is normal, and the edge resolves when you materialize.

When one materialization waits on a still-parked proposal you get exactly one question:

  • --with-deps — pull in what it waits on (recommended)
  • --drop-edges — cut the edge, and record the cut in the phase description
  • abort — nothing changes

--all implies --with-deps and goes in dependency order, which resolves the whole graph without asking per edge.

/audit:propose drop <PROP-id> writes manifest

Parks it as declined, with the reason kept.

/audit:propose revive <PROP-id> writes manifest

Brings a dropped proposal back to proposed.

07

ADO: connecting

The connector is configured in meta.ado in the manifest. Credentials never go there — not in the manifest, not in the config, not in any file. Auth belongs to az or the MCP server, and the secret guard blocks a token that tries to get printed.

/audit:sync connect reads ADO writes manifest

Start here. Four read-only rungs and one write at the end, so nothing is configured until access is proven — and the first thing that proves access is no longer a push, which is also the first thing that can create items on somebody's real board.

  • Transport — the MCP tools if this session has them, else the az CLI plus its devops extension, else install guidance.
  • Which auth path is in effect, reported rather than assumed. A stored token is per organization, so one org can resolve through a token while another resolves through your sign-in, at the same moment. When more than one path is present it names them and picks none.
  • A read-only probe in the Work Items scope — the only scope the connector needs, so it tests what a careful person actually granted.
  • Process detection: one query returns the work item types and the states in use, which settles types.pbi and whether you need a stateMap at all.

Only then does it ask to write organization, project, the proposed types and enabled, and revalidate. Re-running it against a configured manifest re-probes and reports rather than clobbering.

The rest of this section is what connect checks on your behalf. Read it when something stops, or when you want to write meta.ado by hand.

The preflight, in order

Every sync invocation walks the same ladder and stops at the first rung that fails, saying which one. Nothing is read from or written to the board before it passes.

RungFails whenWhat you get
manifest resolvesno manifeststop, pointed at /audit:init
meta.ado existsnever configuredstop, with the setup snippet below
enabledenabled: falsepush/pull stop; status still runs
transportno MCP tools and no azinstall guidance for az extension add --name azure-devops

If meta.ado is missing, this is the block to add to meta:

"ado": { "organization": "<org>", "project": "<project>",
         "areaPath": null, "iterationPath": null,
         "types": { "bug": "Bug", "task": "Task" } }

Everything else — stateMap, sprint, pull, onComplete, comments, echo, phaseWorkItems, enabled — is optional, and the panel's ADO card edits all of them.

A working board command proves the organization is reachable, never which identity reached it

A stored token is per organization. az devops login records it against one org, so on the same machine one organization can resolve through a stored token while another resolves through your Azure sign-in — at the same moment, with no indication which is in play. Measured: with a deliberately invalid AZURE_DEVOPS_EXT_PAT exported, a query against an org that resolves by sign-in still succeeded, so an environment token does not simply override everything.

The order between the three paths is not something to guess at, and /audit:sync connect does not: it reports every path present and picks none when there is more than one. Before a first push, check both az account show and whether a token is stored or exported — a push under the wrong identity does not fail, it writes into the wrong organization.

One more that reads backwards: you need to run the login command does not mean you are logged out. A nonexistent organization produces the same message, so treat it as two readings and check the org name first.

Overlapping iterations break sprint resolution

meta.ado.sprint resolves the current iteration through the team's timeframe. Where a long-running iteration overlaps the numbered sprints — a months-long workstream running alongside them — “current” matches more than one and the stamp lands on the wrong path. A static iterationPath sidesteps the resolution entirely, and sync status prints sprint: unresolvable rather than guessing.

The token, and what it may do

Authentication is per person and per machine. Configuration travels in the manifest and arrives with a merge; access does not — every teammate authenticates themselves.

StepWhat to do
Create the tokenIn the browser profile signed in to the account that has access: User settings → Personal access tokens → New Token
ScopeWork Items → Read & write, and nothing else. That is the whole surface the connector writes: titles, descriptions, state, area, iteration, tags, comments, parent links
Store itaz devops login --organization https://dev.azure.com/<org>, pasted at the prompt — no browser involved, so a machine juggling several accounts is not a problem here
VerifyA WIQL count over the project. It uses exactly the scope you granted, so it tests the thing the plugin will do
Do not reach for Full access

A Work Items token cannot read your source, touch pipelines or cut releases. That narrow scope is what makes a longer expiry a reasonable trade — scope bounds the damage, expiry bounds the duration. With Full access the arithmetic reverses.

Tokens expire. When one does, sync starts returning 401 and it reads like a broken configuration rather than an expired credential — so write the expiry date down where the team can see it.

Find out what the board actually uses

Before configuring anything, one read-only query tells you the process, which decides types.pbi and whether you need a stateMap at all:

az boards query --organization https://dev.azure.com/<org> --project <project> \
  --wiql "SELECT [System.Id],[System.State],[System.WorkItemType] FROM WorkItems
          WHERE [System.TeamProject] = '<project>'" -o json

Read the distinct types and states out of it:

If you seeProcessWhat follows
User Story · New/Active/Resolved/Closed/RemovedAgiletypes.pbi: "User Story"; the built-in stateMap defaults already match — leave it out
Product Backlog Item · New/Approved/Committed/DoneScrumtypes.pbi: "Product Backlog Item"; you must set stateMap — the defaults name Agile states
Board columns are not states

A team can run six columns over four states — “Awaiting feedback”, “In-Progress” and “In Review” all sitting on Active. A card's column lives in per-team hidden WEF_ fields whose id differs per board, and the connector refuses to write them. It sets System.State and lets the team's own column↔state mapping move the card.

So a pushed task lands in the default column for its state, not necessarily the one you had in mind — and a column backed by no state of its own (a review lane, a split Doing/Done) cannot be targeted at all. If a stateMap aims at one, the connector reports the rejection instead of faking the move.

meta.ado.conventions — what an item must look like to belong

Boards usually have a house shape: a description skeleton, mandatory markers, an allowed tag vocabulary, a required parent. Put it in conventions and a conformance gate runs before every create — the payload is checked, and a refusal reaches you before the item exists rather than after somebody has to clean it up.

A board with no conventions block passes and says nothing was checked. That is an answer — “this board has no standard” — not a silent success, and it is worth reading as one.

/audit:sync status read-only

The connector line first — enabled / echo / phaseWorkItems, and the resolved sprint or sprint: unresolvable. Then linked vs unlinked counts, then a row per linked item: manifest id | title | manifest status | ado id | ado state | drift?

It writes nothing on either side and takes no lock. Run it freely — it is the lens you use to decide whether a push is needed at all.

Order that keeps the first mistake small

Verify with /audit:sync status while the plan is still small, then materialize, then push one phase with --phase. A wrong state map then costs a few items instead of a whole board.

Note what that implies on a fresh install: while every phase is still parked there is nothing to push. Proposals are not work items and never become them — only a materialized phase reaches the board. So configuring the connector first costs nothing, and it is the one moment when a misconfiguration cannot create anything.

Conventions the board enforces

meta.ado.conventions carries a board's own house rules, and both keys change what a push may do.

requireParent: true means a card must hang under something. Resolution is phase.adoParent, then meta.ado.parentWorkItem — and on a phase, absent and null are different answers: absent falls through to the manifest-wide id, null does not. Setting neither is not a neutral default. The connector then builds its own branch, which puts audit work beside the team's planning instead of inside it, where nobody planning from that board sees it. The id is an integer; a quoted one is a typo the validator names rather than coerces, because coercing hides it.

tagVocabulary restricts what tags an item may carry — one axis per prefix (type:, supplier:, …), plus "*" for unprefixed tags. The empty list means opposite things on the two. {"*": []} admits any bare tag, because a wildcard with nothing narrowing it is still a wildcard; {"supplier": []} admits no supplier: value. A restriction is something you opt into by listing.

Check the vocabulary against the connector's own tag

The provenance tag defaults to audit-plugin, which carries no prefix — so a board whose vocabulary admits only prefixed tags refuses every item the connector creates, while the manifest still validates clean, because each block is graded alone. Nothing is wrong with either block; they disagree. A prefixed meta.ado.tag closes it.

/audit:sync parents caches what this needs: the project's own backlog ranks and its parent-shaped items. Run it before the first push. Without the cache every parent link reports not verified while the create proceeds anyway — so under requireParent the check abstains at exactly the moment you wanted it to grade. The rank cache carries its own trap, and says so in its basis: it files a bug's rank under whatever meta.ado.types.bug names at fetch time, so renaming that key stops the cached name from matching and bugs begin reading not verified. Re-run the fetch after any such rename.

08

ADO: push & pull

/audit:sync push [bugs|tasks|all] [--task <id> | --phase <id>] writes ADO writes manifest takes lock

Default is bugs. Explicit and idempotent — running it twice does not create duplicates, because the manifest side of each link (ado: {id, url, lastSyncedAt}) is written immediately after each successful call.

  • States are applied by UPDATE, never at create. ADO only accepts the initial state at creation, so every other target state is a second call.
  • A state the process rejects degrades per item — retry without State, report it, and point at stateMap. One bad item does not abort the run.
  • Tags are read-merge-write against the item's existing tag list, never replaced wholesale.
/audit:sync push tasks --phase P0    # one phase, smallest first write
/audit:sync push all                # bugs + tasks + phases
/audit:sync pull [bugs|sprint] writes manifest takes lock

Brings assigned ADO bugs, or the current sprint's items, into the manifest. Never modifies ADO.

The dedup rule is the part worth knowing: a candidate whose id already appears in any manifest ado.id — live tasks, bugs, phases, and parked proposals — is dropped. So a re-pull imports nothing, and parking a proposal does not make its item eligible again.

The two flavours are scoped differently. Both ask before importing anything, so neither can flood you — but do not carry the habit of one over to the other:

  • pull sprint refuses to import blind. It needs an iteration (sprint or iterationPath, else it stops), and it needs a filter — pull.areaPath or pull.tags — because one sprint can span several repositories. With no filter it lists the sprint read-only, makes you pick, and offers to save the filter you chose.
  • pull bugs is project-wide: every non-closed bug, narrowed only by areaPath if one is set. Not sprint-scoped.

Imported sprint items land as parked proposals, one per PBI with its child tasks — nothing enters the live plan until you materialize it.

If your team already tags its cards, that tag is the filter

Most teams mark the cards they own — a supplier tag, a squad name. Put it in pull.tags and a sprint pull sees only your cards in that iteration:

"pull": { "tags": ["<your-card-tag>"] }
Push recognises its own links, and only its own

An item with no ado field is CREATED; one with ado.id is fetched, its mapped fields diffed, and UPDATED only if something differs. That is what makes a repeated push idempotent.

But push does not match by title or tag. A card somebody made by hand for the same phase is invisible to it, and pushing will create a second one. Broad dedup exists only in the other direction. So when the board already holds work that corresponds to your plan: pull first, then push — the pull links them, and the push then updates instead of duplicating.

Decide which phases belong on the board — the manifest cannot say it for you

The plugin proposes phases from what the code needs. Some deliver something a stakeholder recognises; others are “extract this query into a service”. Both are real phases and only the first kind belongs on a shared backlog.

There is no per-phase opt-out today: phaseWorkItems is a global on/off, and the only selectivity is what you name at the call site. Nothing reaches the board by accident — push is never automatic, it prints a plan listing every create, and it confirms before the first write — but the intent lives in people's heads. So make it a team rule and write it down:

/audit:sync push tasks --phase P3    # always name the phase
/audit:sync push all                # the command your team does not run
Where each phase hangs — a board is a tree, and so is this

meta.ado.parentWorkItem is the fallback: one work item that anything undeclared hangs under. Where a sprint spans several Features — each with its own stories and its own tasks — a phase declares its own instead:

"phases": [
  { "id": "P0", "adoParent": { "id": 71157 } },       // this Feature
  { "id": "P3", "adoParent": null },                  // nothing, on purpose
  { "id": "P4" }                                      // whatever the fallback says
]

Three states, and they are three different answers. Absent falls through to the fallback. An object names the parent. Explicit null means this phase hangs under nothing even when a fallback is set — uncategorised on purpose, a legitimate outcome and never an error.

Ask the board for its candidates rather than typing ids from memory:

/audit:sync parents        # caches the backlog levels and the parents you may pick

The push plan then prints the resolved parent per phase, with where it came from — so a fallback that quietly applies to eleven phases and not the twelfth is visible before you confirm, not after.

The plugin checks the tree because ADO does not

Measured, not assumed: ADO does not enforce its own type hierarchy on a link created through the API. A Product Backlog Item really can end up filed under a Task, and the server will not object. So the connector checks it — structurally (an item cannot hang under its own child, and a declared cycle is refused) and, once /audit:sync parents has cached the backlog ranks, by level. Equal rank is a note rather than a refusal, because a Bug under a story is rank-2-under-rank-2 on many boards and teams do it deliberately.

Where the ranks have never been fetched, each item reports not verified rather than being assumed fine.

When the board demands fields the connector does not write

conventions says what an item must have; it can only refuse. meta.ado.fields is the other half — what this project supplies, per work item type, merged into the create payload before the gate grades it:

"fields": {
  "Task":       { "Microsoft.VSTS.Common.Activity": "Development",
                  "Microsoft.VSTS.Scheduling.OriginalEstimate": 4 },
  "User Story": { "Microsoft.VSTS.Scheduling.StoryPoints": 3 }
}

A template may not name a field the connector already maps — that is refused when you write it, because there is no later state in which such a setting quietly starts working. Values are literals; there is no substitution language, because the fields that would carry manifest data are exactly the ones a template may not name.

Read-only fields fail two different ways, and one of them looks like success

System.BoardColumn refuses out loud. But System.Parent, System.Id and System.CreatedBy each create the item, report success, and leave the field unset — measured on a live board. So for the field people most want to set, "try it and report what ADO said" would report a create that worked. That is why naming one in a template is refused at validation instead.

A difference has three readings, not two

When sync status shows drift, the obvious two are “the manifest is ahead” and “the board is ahead”. On a board several teams write to, the common third is: somebody else moved this card after we last touched it, and neither side is wrong. Do not let a push decide that silently — read the drift, then choose.

The reading names the writer, so you can go and ask that person: local ahead — push is the fix, external (<who>, <when>) — push would overwrite it, or unknown — never synced or unstamped, which draws no suggested action because the basis for one is missing.

The board read is one query, and it says what it did

Every linked item is fetched in one query per chunk, not one call per item — the chunk size, the field list and the per-query bound live in a script rather than in prose, because those are the three things prose cannot be held to. The output reports the shape of what it did rather than implying one call, and prints the counts even at zero.

Two exit codes matter and they are not "worked / failed". Exit 0 means every chunk answered and the payload is complete for the ids asked for. Exit 1 means at least one chunk did not answer: the payload is partial, it names the ids it has no news about, and you stop rather than build a table from it — an absent row is not an unchanged one. An id that came back with no row at all is named too, so a work item somebody deleted is a thing you are told, not a row that vanishes from a table that then looks complete.

The real service limit is on the query text, not the number of ids, so the chunker measures the text every time and refuses an oversized query before spending the call — including in a dry run, which is where you want to find that out.

The drift column needs a basis, and the basis is the state map

The comparison is your status translated through stateMap against the board's state — not your status against the board's. The board read does not translate it for you: the map lives in the command, and a second copy in the fetcher would be a second answer. Without it every row reads state not compared (no mapped state supplied) — which is the truth, and is also what a drift table looks like when nobody supplied the map.

So if a whole sync status table says nothing is compared, that is not a clean board. It is a missing map.

On a sharded plan, read the manifest assembled or read almost none of it

In the sharded layout the index holds each phase as a stub — id, title, shard — and nothing else. A phase's own board link and every task's link live in the shard body, so a plain read of the manifest file finds the bugs and stops. Measured on one real plan: a raw read reaches two links, the assembled read reaches sixty-nine.

It does not error. It under-counts, and the connector line looks plausible. The scripts on this path all load assembled; the trap is in any count you compute yourself.

Two settings that stop unwanted writes

A stateMap value of null means never move state for that transition — the field is skipped and the team moves that card by hand. The built-in defaults name Agile-process states; a Scrum project must set stateMap, and /audit:doctor carries that advisory.

10

The panel

/audit:panel [stop|status] [--port <n>] writes manifest

A local control panel for .claude/audit.config.json and the manifest's composition levers, with live validation and discovery of the skills and agents available in this repo and globally. Ephemeral and on-demand; a per-project pidfile keeps it discoverable and stoppable.

Seven sections, in the order they appear:

Overview

Where a run stands: phases, what is ready, what is waiting. The live view — it refreshes from disk while you watch.

Plan & models

Per-phase review model and per-task skills and models. This is where you set which model reviews a phase, without editing the manifest by hand.

Usage

Token spend by phase, task, model, author and time, with cache economics and cost-per-task — the same data as /audit:usage.

Policy

The capability policy: what agents are allowed to do. Expandable full-screen, searchable by name and by description.

Proposals

Parked proposals, materialize and drop — the same script the CLI calls, so both sides behave identically.

Settings

The guard configuration in audit.config.json, validated as you type rather than on save.

Appearance

Theme and presentation for the panel and the rendered report.

What the panel does not cover, stated rather than discovered

The rule is that every feature has a command and a way through the panel. Three places it does not hold today, so you look for them in the terminal and not on screen:

Board status and drift. The ADO card shows manifest evidence only — how many tasks, bugs and phases carry a link, and when the last sync was. It never reads the board, so it cannot show state drift, parent drift or sprint drift. Its own text points you at the CLI, and that is where the answer is: /audit:sync status.

Pulling from the board. There is no panel path at all. Both flavours ask you which items to import, and the panel's manifest writer is deliberately restricted to composition levers — it never changes structure — so it could not apply a pull's result even if it offered one.

Pruning the plan-gate feed. The panel server can do it; the Plan gate card has no button for it yet. Until it does, /audit:logs prune is the way, and --dry-run reports the same counts and writes nothing.

The parent column shows what you declared, never what the board did. The ADO parent cell is your declaration plus the cached candidate list. A phase whose card somebody dragged under a different epic by hand reads exactly the same as one that agrees. /audit:sync status's parent? cell is the surface that knows the difference.

Where panel and CLI are one implementation

Materialize, drop and revive run the same script from either side, and so does the config validator. For those there is no “panel version” of a rule that can drift from the command version — which is why a change made in the panel shows up in /audit:status immediately. The gaps above are missing paths, not second implementations; nothing here has two answers.

What the trail records

Every change to the plan and the config appends one hash-chained row to a journal beside the manifest. It is meant to be committed — that is what makes it evidence rather than a log — and that single fact decides everything else about what a row may hold.

What a row no longer carries, and what stands in its place

It used to storeIt now storesWhy the swap
the command text, verbatim commandSha256, commandBytes, program Arguments are where the paths, hostnames and tokens live. You can still ask “was it this command?” by hashing your candidate.
an absolute cwd a repo-relative path, . at the root, or <outside-repo> Unresolvable, empty and outside all land on the token. A redactor that guesses is a home directory in a file that ships.
actor.host nothing Nothing ever read it. verify does not, no surface renders it, and actor.sessionId already carried the per-session identity. A field with a reader has a redaction question; a field with none has a deletion answer.
the machine name, in the file name the session id, else a random per-checkout token The worst of the four, because the chain is seeded from the file's own base name — a name committed there can never be corrected without breaking verify on every clone that already has the file.
The digest is unsalted, and that is not an oversight

Unsalted is what makes it useful: hashing your candidate is how you check a guess. A salt shipped with the plugin would be published with it, and a per-machine salt would be readable by the same user it hid things from. So a short command from an obvious vocabulary is recoverable by anyone willing to enumerate that vocabulary. This buys friction and data minimisation. It is not anonymisation and must not be sold as it.

Old rows are left exactly as they are

History is not rewritten — the chain runs through those bytes, so correcting a row in place is what breaks verify. Old and new rows share a file and the chain crosses the version boundary intact: a row can be superseded by a later one, never corrected. If you want to know whether anything already committed carries machine identity, that is a question about the files in git, and it is a different question from what the writer does now.

Tamper-evident, not tamper-proof

Editing, deleting or reordering a row breaks the chain and verify names the row. What it cannot stop is a forger who rewrites the whole file and recomputes every hash forward — there is no secret key, and nowhere on a user's machine to keep one the same user cannot read. It is a smoke detector, not a vault.

The other half of what it proves is out-of-band drift: a document that changed with no row to explain it — a checkout, a script, a shell write. Those come back as warnings, not findings, and they are usually the interesting line.

/audit:doctor --deep read-only

Verifies the chain across every journal file, live and archived, and reports drift separately from breakage. This is the command that tells you the trail still holds.
